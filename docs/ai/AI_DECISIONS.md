# EduOS AI Platform — Decisions

Append new decisions; do not rewrite old ones. Mark a replaced decision "Superseded by Dn".

| # | Decision | Reason |
|---|---|---|
| D1 | The trusted AI service is written in .NET 9, like every other EduOS service. | It can reuse `EduOS.ServiceAuth` (JWT validation, session check, tenant middleware) unchanged. A Python service would have to re-implement the security path, which is the part that must not drift. |
| D2 | AI is a separate container (`ai-service`) behind the existing gateway at `/api/v1/ai/*`. No core service calls it. | Failure, load and deployment of AI stay isolated from core EduOS. |
| D3 | Models and embeddings are reached over OpenAI-compatible HTTP behind `IModelProvider` and `IEmbeddingProvider`. | Hugging Face TEI/TGI, llama.cpp, vLLM, Ollama and most hosted APIs all speak it, so changing provider is configuration, not code. Python stays inside untrusted model containers. |
| D4 | A deterministic fake provider is the default in development and CI. | The platform, its security tests and its metering can be built and verified with no model, no GPU and no downloads. The development machine has limited resources. |
| D5 | Vectors live in a separate PostgreSQL instance with pgvector (`ai-db`), not in the core database. | The core database runs `postgres:16-alpine`, which has no pgvector. Swapping its image to a Debian-based pgvector image risks collation and index problems on the existing volume. A separate instance also isolates AI load and failure. |
| D6 | `IVectorStore` takes school id as a required argument, and `ai.chunks` has row-level security on `school_id`. | Tenant isolation is enforced twice, in code and in the database, and cannot be forgotten by a caller. The interface also allows a dedicated vector database later. |
| D7 | v1 indexes only knowledge-base documents uploaded for AI with an explicit audience. Existing `suite.documents` are not indexed. | Those files belong to records whose visibility depends on role and profile links (a parent sees only their child). Reproducing that rule inside a vector index is error-prone; excluding them removes the risk. |
| D8 | Feature flags reuse IAM: permission `enabled` (global), `school_access.allowed` (per school), role grants (per role), plus `ai.school_settings` for quota and tier. | EduOS has no feature-flag system, and IAM already provides exactly these three switches with audit and session revocation. |
| D9 | One `ai.usage_events` row per model or embedding call, written by the gateway pipeline, including failures and cache hits. | Per-school cost, quota enforcement and later billing all read one source. |
| D10 | A router picks the cheapest tier that can answer: direct tool → small model → RAG → strong model. | Most school questions are lookups. This keeps token use and latency low and lets a school's plan cap the tier. |
| D11 | AI does not modify billing tables. Quota is stored in `ai.school_settings`; a later task reads the school's plan to set defaults. | Billing currently stores plan features as display text only and lives in auth-service. Keeping AI separate avoids coupling two unfinished areas. |
| D12 | Ingestion is asynchronous through a jobs table in `ai-db` using `SKIP LOCKED`. | No new infrastructure is needed now, and it can be replaced by a queue when volume requires it. |
| D13 | Tools call EduOS endpoints through the gateway with the caller's bearer token. No service credential is introduced. | Existing RBAC and data scoping apply unchanged. EduOS has no service-to-service credential today (services forward the user token), and v1 does not need one. |
| D14 | Tools are read-only in v1. | Write actions need confirmation UX, idempotency and a separate security review. |
| D15 | Prompt and answer text is not persisted by default. | Conversations can contain children's personal data. Metadata is enough for metering and audit. |
| D16 | Default embedding model is a small multilingual model (384 dimensions, CPU-capable); the model id and dimension are stored with each chunk. | Indian schools use several languages. Recording the model allows re-embedding without guessing. The exact model is confirmed by benchmark in AI-014. |
| D17 | Evaluation sets live in the repository and run in CI against the fake provider. | Isolation and injection regressions are caught without model cost. Quality runs on real models are manual. |
| D18 | AI services start only under the compose profile `ai`. | The default stack, CI and existing deployments are unchanged until AI is switched on. |
| D19 | The AI service's authorization boundary is tested in process with ASP.NET TestHost against the real `AiService.Configure` / `Map` composition, not with Playwright. | It needs no containers or ports, runs in the existing .NET CI job, and exercises the same middleware as production. Playwright is kept for flows that cross services. |
| D20 | Every AI route is listed explicitly in `PermissionAccess`; platform routes (`/api/ai/admin/*`) require the `ai.platform.manage` claim there, not only an endpoint policy. | A new AI endpoint is unreachable until it is mapped, and a forgotten policy on a platform endpoint cannot expose it to a school role. |
| D21 | Two database accounts. The owner (`AI_DB_USER`) is used only by the startup bootstrap to apply migrations; all request work connects as `ai_app` (no superuser, no `BYPASSRLS`, owns nothing). ai-service sets the `ai_app` password from configuration at start. | A bug or injection in request code cannot alter the schema or switch off row-level security. Setting the password from the service avoids a second secret-handling path and allows rotation. |
| D22 | Row-level security is enabled and forced on every table in schema `ai`. The policy is `school_id = ai.current_school()`, which reads the transaction-local setting `ai.school_id`. `AiDatabase.InSchool(tenant, work)` is the only database entry point for request code and sets it from the token. | Unset context is NULL and matches nothing, so a forgotten filter or a missing context returns no rows instead of rows of another school. Transaction-local scope cannot leak through the connection pool. |
| D23 | The `vector` extension is enabled in AI-002, but no vector column or index exists yet. The embedding dimension is intentionally undecided until the embedding model is configured (AI-007, confirmed by benchmark in AI-014). | A wrong dimension would force a table rewrite. Each chunk will record its model, so a later change is an additive re-embedding, not a guess made now. |
| D24 | `ai_app` may only read `school_settings` and only append to `usage_events` and `audit`. There is deliberately no platform-wide path through the database yet. | A school cannot raise its own budget or edit its usage or audit trail. Cross-school reads and settings writes for the Super Admin must be designed explicitly in AI-005 (for example aggregate-only functions), not obtained by loosening the policy. |
| D25 | Every provider descriptor states its `DataBoundary`: `Local` (text stays inside the EduOS deployment) or `External` (text may leave it). | Routing can later refuse or require consent for external providers per school without knowing vendors. The policy itself is still open (Q3). |
| D26 | Providers are only handed out wrapped in `GuardedModelProvider` / `GuardedEmbeddingProvider`. The guard validates the request against the model's limits, requires an explicit output-token limit, enforces the timeout even if the provider ignores cancellation, measures latency, estimates usage when none is reported, checks embedding count and dimension, and maps every failure to `AiProviderException` whose message has no address or key. | These rules hold for every vendor without each adapter re-implementing them, and callers handle one failure type. |
| D27 | The provider contract carries only prepared text, limits and usage: no school, user, credential or cost. Tool calls, the vector-store contract and the HTTP adapter are added by the tasks that first use them (AI-009, AI-007, AI-014). | Authorization and billing stay outside the model layer (S1, S2, S9), and no abstraction exists before something needs it. |
| D28 | A valid, permitted request to an AI endpoint always gets HTTP 200 with `available`: either the result or a fixed reason (`not-configured`, `database-unavailable`, `provider-unavailable`, `provider-timeout`; later `school-disabled`, `quota-exceeded`, `rate-limited`). 400 is only for a bad request, 401/403 for identity and permission. | The frontend handles one shape, a provider problem never looks like an EduOS failure (S17), and no internal detail leaves the service. |
| D29 | The assistant takes one question per request and no history, model name or school. The gateway builds the model request itself: one fixed instruction, the question, and an output limit capped by configuration and by the model. | The context cannot grow from client input, the caller cannot steer the system prompt or pick a costly model, and the school never comes from the request (S2). Conversation memory, if wanted, is a separate decision. |
| D30 | The assistant is available only when `Ai:Enabled` is on and the AI database is prepared, even though AI-004 stores nothing. Until AI-005, which school may use it is controlled only by the IAM permission `ai.assistant.use`. | Metering arrives in AI-005; requiring the database now means there is never a period in which calls are possible but cannot be recorded. Reading `ai.school_settings` waits for the PostgreSQL runtime validation. |
| D31 | Rate limiting is in memory inside ai-service: requests per user and per school in fixed one-minute windows, identities from the verified token, limits from `Ai:Limits`. It runs after the feature-state check and before validation, so invalid requests count but refused ones do not. A limited caller gets `rate-limited` with `retryAfterSeconds`. | It protects the service with no new dependency, and its state is bounded to the identities seen in the current minute. **It is per process.** With more than one ai-service instance each enforces its own limit, so a multi-instance deployment needs a shared store or an equivalent limit at the gateway. This is separate from the per-school quota (AI-005), which is an allowance, not protection. |
| D32 | One circuit breaker per provider name, in memory. Every `AiProviderException` (timeout, unavailable, invalid response) counts as a failure; a success resets the count; rejected, unauthorized, rate-limited and caller-cancelled requests are never counted. At the threshold the circuit opens for the recovery interval, then one trial call is allowed: success closes it, failure reopens it for a full interval. While open, callers get `provider-unavailable` and status reports the same. | An unhealthy provider is not called repeatedly, user mistakes cannot take the assistant down, and callers cannot tell a tripped circuit from any other provider outage. Like D31 it is per process. |
| D33 | The allowance is a monthly token budget per school (calendar month, UTC) in `ai.school_settings`. Before a model call the gateway reserves the worst case of that call (estimated input plus the full output limit) in `ai.usage_reservations`, in one transaction serialised per school by an advisory lock. The request is admitted only if tokens spent this month, reservations in progress and its own worst case fit in the budget. After the call the reservation is deleted and the real usage is written in the same transaction; a reservation that is never settled expires after the provider timeout plus 30 seconds. | Simultaneous requests cannot spend the same allowance, a school can overshoot by nothing, and a crashed call cannot block the allowance for long. The cost is that the last request must fit in full. `ai_app` gains DELETE on reservations only; usage and audit stay append-only and settings read-only (D24 otherwise unchanged). |
| D34 | Failure rules for metering. If the switch or allowance cannot be read, the request is refused with `database-unavailable` and no model call is made. A failed or timed-out provider call is recorded (`success = false`, error code, the input that was sent, marked estimated) but not charged to the allowance. If a call succeeds but its usage cannot be written, the answer is withheld and the token counts are logged for reconciliation. A cancelled request releases its reservation. | The school is never served outside its accounted allowance and never charged for an answer it did not get. Withholding an answer is rare and visible in the log; serving unmetered answers would be silent. |
| D35 | A school with no `ai.school_settings` row is switched off. Status and the usage endpoint report the school's own state (`school-disabled`, `quota-exceeded`) through the same store. | Default deny per school, and the frontend can hide the assistant without trying a question. |
| D36 | Task numbers after AI-008 were changed on 2026-10-02. Old → new: AI-006 (ingestion with embedding) split into AI-006 (ingestion) and AI-007 (embeddings and vector storage); AI-007 retrieval → AI-008; AI-008 RAG answer → AI-009; AI-014 local model runtime and HTTP adapter → AI-010; AI-009 tools → AI-011; AI-010 routing → AI-012; AI-011 frontend → AI-013; AI-012 admin pages → AI-014; AI-013 evaluation → AI-015; AI-015 billing hook → AI-016; AI-016 hosted provider → AI-017. AI-005B is deferred, not cancelled. Completed task numbers are unchanged. | The knowledge path is built in the order ingestion, embeddings, retrieval, RAG integration, then the first real model. Earlier decisions (D16, D23, D27, Q1–Q3) cite the old numbers; read them through this map. |
| D37 | Knowledge is stored as text chunks only. The uploaded file is read in memory, turned into normalised text, chunked and discarded: no raw file, no full-text copy and nothing on disk. A document row and all its chunks are written in one transaction with status `ready`; the other statuses (`pending`, `processing`, `failed`) exist for the asynchronous embedding step in AI-007. The same normalised text is kept once per school (SHA-256, unique per school). A chunk references its document by `(school_id, document_id)`. | One copy of the content, nothing half-written to search later, and no file-system surface. Per-school de-duplication reveals nothing across schools. The two-column reference makes it impossible for a chunk to sit under a document of another school even if row-level security were bypassed. `ai_app` may insert and read both tables and delete documents (chunks go with them); it cannot update either. |
| D38 | Chunking is deterministic and uses no model: at most `Ai:Knowledge:ChunkMaxChars` characters (default 1200, about 300 tokens), overlap of `ChunkOverlapChars` (default 150) starting at a word boundary. In Markdown a heading always starts a new chunk and the chunk records that heading as its section; otherwise a chunk ends at a paragraph, line, sentence or word boundary found in the second half of its window. Each chunk keeps its order and character range in the normalised text; `page` is reserved for paged formats. | Zero model cost, repeatable results, and exact section and offset data for citations. Sections are never mixed in one chunk, which keeps a cited section truthful. |
| D39 | Supported formats are UTF-8 plain text (`.txt`) and Markdown (`.md`, `.markdown`), decided by extension and checked by content. PDF, Office formats and OCR are not supported yet. | No PDF library is in the approved local package cache, and adding one needs a dependency decision. Text and Markdown need no new dependency and cannot carry executable content. |
| D40 | Every knowledge document has an explicit audience (any of `school`, `teacher`, `parent`, `student`, matching the token's data scope). Managing knowledge needs `ai.knowledge.manage`, the deployment switch and the school's AI switch, and is rate-limited with the same limiter as the assistant. It charges no token quota, because it calls no model. | Retrieval (AI-008) will filter by audience, so it must be recorded at upload. A school that is switched off cannot build knowledge either. |
| D41 | The vector storage has one explicit active **embedding space**: a row in `ai.embedding_spaces` holding provider, model and dimension, with exactly one row active. Its dimension comes from `IEmbeddingProvider.Descriptor` and is settled when the database is prepared at start-up: the first provider ever configured becomes the active space; the same provider reuses it; a different model or dimension is a mismatch and embedding stays off (`embedding-unavailable`) unless `Ai:Knowledge:AdoptEmbeddingModel` is on, in which case the new space becomes active and existing documents report `pending` until embedded again. No dimension is written in application code or in a migration. This settles D23. | A model change is an explicit operational act, never a silent reinterpretation of old vectors. Vectors of different models are never mixed, because every vector row and every ready document names its space. |
| D42 | `ai.knowledge_embeddings` has one row per chunk and space, with an untyped pgvector column. A check ties the vector's size to the row's `dimension`, and a two-column reference ties that dimension to the space's, so a vector can be neither cut nor padded to fit. Another two-column reference ties the row to a chunk of the same school. The chunk text is not repeated. Vectors are derived data: `ai_app` may insert and delete them, never update them. | The database enforces the dimension and the school even if application code is wrong. An untyped column lets a later model with another dimension live in a new space without changing the table. |
| D43 | Embedding is its own step (`KnowledgeEmbedder.Embed(tenant, documentId)`), run right after a successful upload and also on demand. It sends the provider the chunk texts only, in batches of `Ai:Knowledge:EmbeddingBatchSize` (never more than the provider accepts), and checks the count and the dimension of every response. All vectors of the document and its `ready` state are written in one transaction (`IKnowledgeStore.CompleteEmbedding`), which fails and changes nothing unless every chunk has exactly one vector. On any failure the document stays stored, is marked `failed` with a safe reason, keeps no partial vectors, and can be embedded again; repeating it replaces the vectors and never duplicates them. A ready document that fails a later re-embedding keeps its state and its vectors. | "Ready" always means fully embedded in one space. The step takes only a tenant and a document id, so a background worker can call it later without changing the store. Vectors and document state share one store because they must change together; this replaces the separate `IVectorStore` foreseen in D6 and D27, whose rule (the school is a required argument of every method) still holds. |
| D44 | No approximate-search index yet. Search (AI-008) will be an exact scan of one school's vectors in the active space, supported by an index on `(school_id, space_id)`. The distance will be cosine (`<=>`), which suits normalised text embeddings and the unit vectors of the fake provider. When a school outgrows an exact scan, an HNSW index is added for the active space's dimension. | At the expected size per school an exact scan is fast and always correct, and it needs no dimension in the schema. Approximate search and its tuning are deferred until measured. |
| D45 | Embedding is not metered in `ai.usage_events` and does not touch the assistant's monthly allowance. The tokens embedded are kept on the document (`embedded_tokens`, `embedded_at`) and logged with the provider, model and duration. | The allowance rules of AI-005 stay exactly as they were. Embedding activity is still visible per document, clearly apart from assistant usage, without inventing cost accounting. |
| D46 | Retrieval is one service, `KnowledgeRetriever.Retrieve(tenant, audience, question, request)`, which callers use without knowing PostgreSQL. It checks the deployment and school switches, validates the question, embeds it with the configured provider (the question text only), requires the provider to match the active embedding space, and runs `IKnowledgeStore.Search` through `AiDatabase.InSchool`. The search filters by school, space, dimension, `ready` state and audience in the query itself and repeats the school on both joins; row-level security on all three tables bounds it independently. The audience is the caller's data scope from the token. | The assistant (AI-009) gets a provider-neutral list of chunks and cannot widen the search. Two independent boundaries hold: removing the school filter from the query was tested against real PostgreSQL and still returned only the caller's rows. |
| D47 | The search is exact: every vector of the school in the active space is compared by cosine distance (`<=>`), ordered by distance, then document, then chunk order. No HNSW or IVFFlat index exists and the result does not depend on one. A mismatch between provider and active space, or a malformed query vector (wrong count, wrong dimension, non-finite, all zero), means no search at all. | Exact search is always correct and fast at the expected size per school, and needs no dimension in the schema (D44). Comparing against vectors of another model would return confident nonsense, so it is refused rather than attempted. |
| D48 | Retrieval is bounded four ways under `Ai:Retrieval`: question length (1000 characters), results (`TopK` 5 by default, a caller may ask for up to `MaxTopK` 10, and nothing can exceed the hard maximum of 20), a minimum cosine similarity (0.5 by default, to be calibrated per embedding model), and a context budget (`MaxContextChars` 6000, never less than the chunk size). Selection takes candidates in rank order and stops at the first one below the threshold, at the count, or at the first chunk that does not fit the budget; it never cuts text and never reaches past a chunk that does not fit for a less relevant one. A chunk is skipped when its text is already selected or when more than half of it lies inside a selected chunk of the same document; neighbouring chunks, which share only their overlap, are both kept. When nothing passes the threshold the result is empty. | The context a model can ever be given is bounded before AI-009 exists, and irrelevant text is never forced into it. The rule is deterministic and uses no model. |
| D49 | `POST /api/ai/knowledge/search` is a diagnostic for people with `ai.knowledge.manage`: it returns the chunks of their own school that a question would retrieve, with text and similarity, never a vector, space or provider. They may ask as another audience of their school to check a document's reach. It is rate-limited at the endpoint. The retriever itself applies no rate limit, so the assistant can call it inside a request that was already admitted. Retrieval calls no model, is not metered and charges no quota. | Knowledge managers can already read and remove every document of their school, so previewing an audience widens nothing. Putting the rate limit at the entry point avoids counting one user request twice in AI-009. |
| D50 | Order of an assistant request: feature state and open model circuit → rate limit → question and output limits → retrieval for the school and data scope of the token → if nothing relevant, stop → build the bounded context → reserve the worst case of the final request (its input plus the output limit) → circuit breaker → model → record usage and settle. Retrieval comes before the reservation, so a question that generates nothing holds and charges nothing; the query embedding is never charged. The request body carries a question and an output limit only: no school, audience, role or document can be supplied. | The allowance is held for exactly what the model is sent (D33 still holds). The cost of this order: a school with no allowance left can still cause query embeddings, bounded by the rate limit. |
| D51 | Retrieved documents are untrusted data, and the boundary is structural. The model is sent three messages: a constant instruction that never contains document text; the reference material as a message of its own, each chunk between `[source N]` and `[end of source N]` with its title, section and page; and the caller's question, alone, last. Marker-like text inside a chunk, title or section is made inert, and titles and sections are kept on one line. The instruction says the material is information, not instructions, and that unsupported facts about the school must not be stated. No heuristic injection detection. The model gets no school, user, permission, document identifier, file label or score. | A document can say anything, but it cannot become the instruction, the question or a source of its own. An adapter for a model whose template needs alternating roles (AI-010) must keep material and question distinguishable when it merges them. |
| D52 | No chunk above the threshold: the answer is `available: false, reason: "insufficient-knowledge"`, with no model call, no reservation and no usage row. A failure of retrieval is never replaced by an ungrounded answer: embedding provider failure, timeout or a mismatched embedding space give `retrieval-unavailable`; `database-unavailable`, `school-disabled`, `not-permitted` (a data scope the knowledge base does not know) pass through. Neither outcome touches the model's circuit breaker; an open circuit refuses the request before anything is embedded. Model failures keep `provider-unavailable` and `provider-timeout`. `available: true` therefore still always means an answer is present. | The model is never asked to invent facts about a school. Reasons stay machine-readable and distinct, and existing clients keep the meaning of `available`. |
| D53 | Sources are decided by the service, never read from the model's text: one entry per place (document, section, page) whose chunks were actually in the material, in ranking order, numbered as in the material. Each has `number`, `documentId`, `title`, `source` (the upload's file label), `section`, `page`. No chunk identifier, vector, score, school or path. They are returned only with an answer. The usage row records how many chunks were used (`retrieved_chunks`). | The citation list cannot be invented or widened by a model or a document. |
| D54 | The model input is bounded by the lower of the model's own input limit and `Ai:Assistant:MaxRequestTokens` (4096) less the output asked for. Chunks are added in ranking order and the first one that does not fit ends the context; a chunk is used whole or not at all, and nothing is summarised. If not even the best chunk fits, the request is refused (400) rather than answered without evidence. The question limit of the assistant is the lower of `Ai:Assistant:MaxQuestionChars` and `Ai:Retrieval:MaxQueryChars` (both 1000). Answers are returned as plain text in JSON; rendering them inert (S11) is the frontend's task (AI-013). | One request can never hold more of the allowance than the request budget, and the provider guard's input check can never be the thing that fails. |
| D55 | Real models are reached through one adapter pair, `LocalModelProvider` and `LocalEmbeddingProvider` (provider name `local`), which speak the OpenAI-compatible HTTP protocol (`/chat/completions`, `/embeddings`) and know nothing about the runtime or model behind the address. Chat and embeddings are selected separately (`fake` or `local`); there is no fallback from one provider to another and none to any cloud. The endpoint must be loopback; `AllowPrivateNetwork` permits a private address or a single-label name on the deployment's own network and never a public one; an address with credentials or a query is refused. The client uses no proxy, follows no redirect, keeps no cookie and sends no credential, because the service holds none. | Any OpenAI-compatible local runtime (llama.cpp server, Ollama, others) can be swapped by configuration. Text cannot leave the deployment through this provider, so `DataBoundary.Local` stays true. |
| D56 | The local runtime is untrusted. Every call still goes through the provider guards (limits, timeout, error mapping) and, for chat, the circuit breaker and quota. An error body is never read (it can repeat the prompt); a failure is only `Unavailable`, `Timeout` or `InvalidResponse`. The model name recorded and returned is the configured one, never the runtime's (which can be a file path). Token usage is taken from the runtime only when it reports both counts as positive numbers; otherwise it is estimated and marked. An answer of more than four times the output limit, an empty answer, a reply over the size cap (1 MB chat, 32 MB embeddings), and vectors that are missing, repeated, misplaced or of another size are refused. Limits (`MaxInputTokens`, `MaxOutputTokens`, `Dimension`, `MaxBatchSize`) are configured, in the platform's four-characters-per-token estimate, and must leave headroom below the runtime's real context. | A misbehaving or replaced runtime can fail a request but cannot leak through errors, overspend an allowance unnoticed, store a wrong vector or put a path into usage records. |
| D57 | The adapter sends the three RAG messages as they are (`Messages: separate`). For a model whose chat template needs alternating turns, `Messages: merged` joins consecutive user messages into one turn: the later one goes under a fixed `[user message]` label and the same words inside the earlier text are made inert. The system message is never joined with anything. This lives only in the adapter. | The trust boundary of D51 holds for every template: document text never reaches the system message, and the question stays last and marked. |
| D58 | A real embedding model is a new embedding space (provider, model, dimension). It is activated only by starting the service once with `Ai:Knowledge:AdoptEmbeddingModel=true`; without it the service reports `embedding-mismatch` and neither embeds nor searches. After activation the documents of the old space are no longer searched until each is embedded again (`POST /api/ai/knowledge/documents/{id}/embedding`), which writes its vectors of the new space in one transaction. Vectors are kept per space (`chunk_id`, `space_id`): those of the earlier space stay stored, are never converted and are never searched while the document belongs to the new space; nothing removes them yet. Rolling back is the same step with the earlier provider configured, followed by embedding again. `Ai:Retrieval:MinSimilarity` is calibrated again for the new model. First models, chosen for the 7.3 GB CPU-only development machine and to be confirmed by measurement: llama.cpp server as the runtime, `bge-small-en-v1.5` (MIT, 384 dimensions, English) for embeddings, `Qwen2.5-1.5B-Instruct` Q4_K_M (Apache-2.0) for chat. | Spaces of different models are never mixed (D42). The model choice is configuration, so a larger or multilingual model replaces these without code changes. |
| D59 | For `bge-small-en-v1.5` the similarity threshold is `Ai:Retrieval:MinSimilarity = 0.65`, set where that model is configured; the built-in default stays 0.5, which belongs to the fake provider. Measured on 2026-10-02 with one synthetic policy document (6 chunks) and 10 questions: the correct chunk scored 0.742 to 0.878 for six related questions; the best chunk for four unrelated questions scored 0.366 to 0.634 (a swimming-pool question against the library and sports chunks was the highest). At 0.5 an unrelated question reached the model and related questions carried up to five chunks, three of them off-topic; at 0.65 unrelated questions stop at `insufficient-knowledge` and related ones carry one or two chunks, with the same correct answers. The sample is small: the value is provisional until the evaluation set (AI-015) confirms it. With local CPU inference `Ai:Providers:TimeoutSeconds` must be raised from 30 (a full context took 40 s here); 120 is the recommended value. | The threshold depends on the embedding model, as D48 said. Scores of this model sit high and close together, so the fake provider's value lets irrelevant text through. |
| D60 | Ask EduOS AI (AI-011) is a presentation layer over the AI Gateway and adds nothing to the backend. It is a button in the top bar, shown to school users whose session holds `ai.assistant.use` (never to the platform administrator), that opens a panel. It calls `POST /ai/assistant/ask` through the existing API client and sends the question only: no school, audience, role, document, permission or earlier message. The backend stays single-turn: the panel keeps the conversation in memory for the signed-in session (lost on refresh, sign-out or a change of account), writes nothing to browser storage or any database, and says that each question is answered on its own. Sources shown are exactly the list the backend returned (title, section, page, file label; no identifier), never derived from the answer text. Answers, sources and questions are rendered as plain text: no HTML, no Markdown, no links made from model output (S11). Every backend reason maps to a fixed sentence; the reason, the model, the runtime and any error text are never displayed. The panel states that operational data (attendance, fees, marks, records) is not available: only uploaded knowledge is.
