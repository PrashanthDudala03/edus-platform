# EduOS AI Platform — Decisions

Append new decisions; do not rewrite old ones. Mark a replaced decision "Superseded by Dn".

| # | Decision | Reason |
|---|---|---|
| D1 | The trusted AI service is written in .NET 9, like every other EduOS service. | It can reuse `EduOS.ServiceAuth` (JWT validation, session check, tenant middleware) unchanged. A Python service would have to re-implement the security path, which is the part that must not drift. |
| D2 | AI is a separate container (`ai-service`) behind the existing gateway at `/api/v1/ai/*`. No core service calls it. | Failure, load and deployment of AI stay isolated from core EduOS. |
| D3 | Models and embeddings are reached over OpenAI-compatible HTTP behind `IModelProvider` and `IEmbeddingProvider`. | Hugging Face TEI/TGI, llama.cpp, vLLM, Ollama and most hosted APIs all speak it, so changing provider is configuration, not code. Python stays inside untrusted model containers. |
| D4 | A deterministic fake provider is the default in development and CI. | The platform, its security tests and its metering can be built and verified with no model, no GPU and no downloads. The development machine has limited resources. |
| D5 | Vectors live in a separate PostgreSQL instance with pgvector (`ai-db`), not in the core database. | The core database runs `postgres:16-alpine`, which has no pgvector. Swapping its image to a Debian-based pgvector image risks collation and index problems on the existing volume. A separate instance also isolates AI load and failure. |
| D6 | `IVectorStore` takes school id as a required argument, and `ai.chunks` has row-level security on `school_id`. | Tenant isolation is enforced twice, in code and in the database, and cannot be forgotten by a caller. The interface also allows a dedicated vector database later. |
| D7 | v1 indexes only knowledge-base documents uploaded for AI with an explicit audience. Existing `suite.documents` are not indexed. | Those files belong to records whose visibility depends on role and profile links (a parent sees only their child). Reproducing that rule inside a vector index is error-prone; excluding them removes the risk. |
| D8 | Feature flags reuse IAM: permission `enabled` (global), `school_access.allowed` (per school), role grants (per role), plus `ai.school_settings` for quota and tier. | EduOS has no feature-flag system, and IAM already provides exactly these three switches with audit and session revocation. |
| D9 | One `ai.usage_events` row per model or embedding call, written by the gateway pipeline, including failures and cache hits. | Per-school cost, quota enforcement and later billing all read one source. |
| D10 | A router picks the cheapest tier that can answer: direct tool → small model → RAG → strong model. | Most school questions are lookups. This keeps token use and latency low and lets a school's plan cap the tier. |
| D11 | AI does not modify billing tables. Quota is stored in `ai.school_settings`; a later task reads the school's plan to set defaults. | Billing currently stores plan features as display text only and lives in auth-service. Keeping AI separate avoids coupling two unfinished areas. |
| D12 | Ingestion is asynchronous through a jobs table in `ai-db` using `SKIP LOCKED`. | No new infrastructure is needed now, and it can be replaced by a queue when volume requires it. |
| D13 | Tools call EduOS endpoints through the gateway with the caller's bearer token. No service credential is introduced. | Existing RBAC and data scoping apply unchanged. EduOS has no service-to-service credential today (services forward the user token), and v1 does not need one. |
| D14 | Tools are read-only in v1. | Write actions need confirmation UX, idempotency and a separate security review. |
| D15 | Prompt and answer text is not persisted by default. | Conversations can contain children's personal data. Metadata is enough for metering and audit. |
| D16 | Default embedding model is a small multilingual model (384 dimensions, CPU-capable); the model id and dimension are stored with each chunk. | Indian schools use several languages. Recording the model allows re-embedding without guessing. The exact model is confirmed by benchmark in AI-014. |
| D17 | Evaluation sets live in the repository and run in CI against the fake provider. | Isolation and injection regressions are caught without model cost. Quality runs on real models are manual. |
| D18 | AI services start only under the compose profile `ai`. | The default stack, CI and existing deployments are unchanged until AI is switched on. |
| D19 | The AI service's authorization boundary is tested in process with ASP.NET TestHost against the real `AiService.Configure` / `Map` composition, not with Playwright. | It needs no containers or ports, runs in the existing .NET CI job, and exercises the same middleware as production. Playwright is kept for flows that cross services. |
| D20 | Every AI route is listed explicitly in `PermissionAccess`; platform routes (`/api/ai/admin/*`) require the `ai.platform.manage` claim there, not only an endpoint policy. | A new AI endpoint is unreachable until it is mapped, and a forgotten policy on a platform endpoint cannot expose it to a school role. |
| D21 | Two database accounts. The owner (`AI_DB_USER`) is used only by the startup bootstrap to apply migrations; all request work connects as `ai_app` (no superuser, no `BYPASSRLS`, owns nothing). ai-service sets the `ai_app` password from configuration at start. | A bug or injection in request code cannot alter the schema or switch off row-level security. Setting the password from the service avoids a second secret-handling path and allows rotation. |
| D22 | Row-level security is enabled and forced on every table in schema `ai`. The policy is `school_id = ai.current_school()`, which reads the transaction-local setting `ai.school_id`. `AiDatabase.InSchool(tenant, work)` is the only database entry point for request code and sets it from the token. | Unset context is NULL and matches nothing, so a forgotten filter or a missing context returns no rows instead of rows of another school. Transaction-local scope cannot leak through the connection pool. |
| D23 | The `vector` extension is enabled in AI-002, but no vector column or index exists yet. The embedding dimension is intentionally undecided until the embedding model is configured (AI-007, confirmed by benchmark in AI-014). | A wrong dimension would force a table rewrite. Each chunk will record its model, so a later change is an additive re-embedding, not a guess made now. |
| D24 | `ai_app` may only read `school_settings` and only append to `usage_events` and `audit`. There is deliberately no platform-wide path through the database yet. | A school cannot raise its own budget or edit its usage or audit trail. Cross-school reads and settings writes for the Super Admin must be designed explicitly in AI-005 (for example aggregate-only functions), not obtained by loosening the policy. |
